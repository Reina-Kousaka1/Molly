# Molly V1.2 — developer and lifecycle controls

These features are part of Molly **V1.2**, not V2.

## Global blacklist

`/blacklist add`, `/blacklist remove`, and `/blacklist check` are restricted to Discord IDs explicitly listed in `MOLLY_DEVELOPER_IDS`. Entries are stored in Molly-owned SeaWorld collection `molly_global_blacklist` with user ID, reason, timestamp, and responsible developer ID. The command router performs one central blacklist gate for ordinary commands; developer/owner commands bypass only that gate so the blacklist can still be administered. Mutation receipts use Discord interaction IDs for retry idempotency and retain the newest 1,000 IDs; expired IDs fail closed with `replay_expired`. Active blacklist entries are not automatically evicted, so their total count remains a document-growth risk.

Lifecycle restart/update receipts also retain at most 1,000 interaction IDs and reject expired replays. The single pending lifecycle marker is retained separately. Canceling a marker removes its receipt, matching the existing cancel behavior.

## Developer inspector

`/eval` is a name for a fixed, read-only operation set. It does **not** evaluate Lua. Available subcommands are `db-user`, `db-balance`, `db-transactions`, `db-transaction`, `db-inventory`, `guild`, `cooldowns`, `tree`, `runtime`, `errors`, and `seaworld`.

The transaction inspector uses the economy journal that already exists in Molly. Existing records contain only `id`, `guild`, `user`, `kind`, `amount`, `counterparty`, `timestamp`, and `status`; the inspector does not invent additional fields. History is capped at 20 entries. The current economy has no inventory model and the logger has no persistent error ring, so those operations explicitly report unavailable instead of fabricating data.

The inspector cannot execute Lua, SQL, shell commands, processes, filesystem operations, arbitrary SeaWorld requests, Docker operations, environment dumps, network requests, or secret reads. Discord administrator/moderator/guild-owner status grants no access by itself.

## Shutdown and restart

`/shutdown` is owner/developer-only, acknowledges the interaction, closes Molly/SeaWorld through the existing shutdown path, closes Discord, and exits with code `0`.

`/restart` stores a SeaWorld-backed lifecycle marker containing the original guild/channel, requester, optional reason, timestamp, and interaction ID. It then shuts down cleanly and exits with code `75`. Duplicate interaction IDs are idempotent.

The checked-in systemd unit already uses `Restart=on-failure`, which leaves exit `0` stopped and restarts exit `75`. The checked-in Compose definition is changed to `restart: "on-failure:5"` for the same distinction. This repository change is **not** a production deployment; the Raspberry Pi configuration must be updated separately after review.

## Update architecture

`/update` never accesses `/var/run/docker.sock`. Molly can only send a small authenticated POST to a loopback-only updater URL configured by `MOLLY_UPDATER_URL` plus `MOLLY_UPDATER_TOKEN`. The request contains only the fixed `update` action and lifecycle identifiers. If both settings are absent, `/update` returns `Update service unavailable/not configured.` and does not claim success.

The external updater is intentionally not activated by this repository change. On the Raspberry Pi it must be a separately privileged, Molly-only service that authenticates the token, accepts only the fixed update action, fetches/builds the intended Molly revision, runs tests/checks, swaps only Molly after success, preserves the last known-good deployment on failure, and verifies startup health. It must not expose a shell, generic Docker API, arbitrary image/container names, or host Docker socket to Molly.

After the updater accepts a request Molly exits with code `76`. The external updater/supervisor must coordinate that exit so an old image is not simply restarted before replacement.

## Post-restart/update health

A normal startup has no lifecycle marker and sends no recovery message. For restart/update, Molly waits for Discord ready and then uses the normal application health snapshot. A recovery message is sent only when the snapshot is fully healthy, including SeaWorld. Only after Discord accepts that message is the pending marker cleared, so a failed startup cannot falsely report success and a successful marker produces one message.

## SeaWorld

Molly continues to use its existing Unix-socket SeaWorld adapter and negotiates a compatible SeaWorld 1.x API with native queries, field updates, and transactions. This work does not pin SeaWorld to `main`, does not pin the older `v1.1.0-beta.1`, and does not change SeaWorld itself. Global state uses isolated connector sessions just like guild persistence, while the existing guild store retains per-guild locking rather than a global guild lock.

## Raspberry Pi deployment still required

No production, Raspberry Pi, running-container, or Docker action is performed by this change. Before enabling lifecycle commands in production: configure explicit developer IDs; deploy the reviewed supervisor restart policy; provision the Molly-only updater and its secret if live update is desired; set build version/commit metadata; then verify restart, shutdown, updater rollback, and post-health messaging in a staging deployment.
